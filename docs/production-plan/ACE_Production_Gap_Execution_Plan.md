### 1.1 The build, in one view (added in v8 — the totality, so scaffolding never obscures it)

## 4. Architecture doctrines (binding on all specialists)

1. **Seam pattern, with a configuration-driven mode registry (amended in v12).** Every engine lands behind an interface the existing screens already call; authored demo data remains a selectable mode. The scattered Mock Data toggles consolidate into one **mode registry**: a `dataMode` setting per seam with values `mock | seeded | production`, read from environment in development and from `deploy.config.yaml` in deployment (D5 schema gains this key block). Switching any seam to production is a configuration change, never a code change. The C5 dual-mode walkthrough asserts every seamed screen renders correctly in mock AND non-mock modes per phase. Demo stays green through every phase.
2. **Contracts before components.** No specialist designs until the spine publishes the contract register (Section 6).
3. **Three-lane execution.**
   - Batch lane: DAG pipelines. Steps are containers with declared inputs/outputs + idempotency keys. Airflow is the reference orchestrator (managed Airflow exists on AWS MWAA / GCP Composer / Azure ADF). Adapters to ADF / Step Functions only if a customer mandates them. Streams never run in Airflow.
   - Stream lane: event backbone. Partitioned queue, partition key = memberId (guarantees per-member ordering the SDE requires), idempotent consumers, DLQ + replay.
   - Journey lane: durable workflows for long-lived member journeys (multi-day human-in-the-loop waits, timers such as 72-hour scheduling windows), with retries + state.
4. **Scale doctrine: design for linear scale, prove at 10x pilot.** Stateless partitioned workers from day one; load-test gates at 1K/min sustained, 5K/min burst, 10K/min headroom; documented linear-scale argument (partitions + pods) to 100K/min. CPU-bound match scoring uses blocking keys (DOB / zip / phonetic) to bound candidates, worker_threads pool for scoring. HAPI posture: clustered nodes + tuned Postgres + async boundary validation; CQRS reads from projections.
5. **Portability doctrine: no proprietary control plane in the core.** Core services depend only on open protocols: Postgres wire, Kafka API, S3-compatible object storage, OIDC, container runtime. Anything hyperscaler-specific lives in the IaC layer (Terraform modules per cloud). Durable workflow engine must be self-hostable (Temporal-class), never Step Functions / Durable Functions in the core.
6. **FHIR store as a seam.** HAPI self-managed is the reference implementation; managed FHIR services (AWS HealthLake / Azure Health Data Services / Google Cloud Healthcare API) are conformance-gated adapters on the roadmap. A conformance test suite gates any swap.
7. **Deployment configurability, phased honestly.** v1: `deploy.config.yaml` (cloud, region, managed-vs-self choices per tier) driving per-cloud Terraform stacks through CI. v2: an admin-console Deployment screen that renders + drives the same engine. The screen is the face; IaC is the engine.
8. **Effort grammar.** S/M/L with explicit assumptions plus named spike tickets. No fake week-precision.
9. **Documentation doctrine (new): docs-as-code, audience-tagged, state-labeled.**
   - Docs live in the repo (`docs/`), versioned with the code, generated from source wherever possible (API reference from route definitions, contract docs from schemas, deployment guides rendered from `deploy.config.yaml`). Hand-maintained copies of generatable content are forbidden — they go stale.
   - Every document declares its audience and whether it describes **current state or target state**. No document may imply production capability that today exists only as demo surface. This is the documentation twin of the demo honesty guardrails.
   - Two classes, adversarially enforced: **authored-now** docs (truthfully writable from this session's verified evidence) and **build-gated** docs (a template plus acceptance criteria attached to the epic that makes them true — an epic is not done until its runbook section, API entries, and deployment notes exist). Nobody writes operational fiction for systems that do not exist yet.
   - Docs-stay-current is a regression contract like demo-stays-green: a PR that changes a seam, contract, or deployment surface without touching its doc fails review.
10. **House coding conventions are binding (new in v6; referent updated).** The governing standard is now `AI-CODING-CONVENTIONS.md` **v2** at repo root (adopted and committed in this session; v1 archived at `docs/archive/AI-CODING-CONVENTIONS.v1.md`, out of scope going forward). ## 4A. Pipeline reference architecture (new in v9 — binding on G3/X2; specialists design WITHIN this, they do not reinvent it)

**Five stages. Every feed, every domain, both lanes.**

1. **Land.** Raw capture of every inbound format, immutable, replayable: FHIR (API push/pull, bulk `$export` NDJSON), X12 (834 / 837 / 835 / 278), flat files (CSV / pipe-delimited SFTP drops — first-class, because CBO and social-sector data arrives this way), C-CDA/CCD XML from QEs, HL7v2 (ADT streams), JSON/webhook (screening tools, closed-loop referral platforms). Object storage, cataloged (source, received-at, batch id, checksum). Nothing is transformed here; landing is the audit + replay foundation.
2. **Stage + validate.** Explicit staging tier — structural validation per format (X12 envelope, CCD schematron, schema checks), a quarantine lane for rejects with a remediation workflow, PHI-safe rejection reporting. Bad records never silently vanish and never poison a load.
3. **Transform + enrich (in-flight processing).** Source adapters normalize to the canonical domain model (the `NormalizedPolicy` pattern, applied to every domain); terminology normalization (ICD-10, SNOMED, LOINC, RxNorm, Gravity Z-codes/value sets); identity resolution via the existing match engine (member link, provider NPI resolution) — the record attaches to the anchored identity, never to raw source ids; **consent + 42 CFR Part 2 segmentation labels applied here, at transformation time** — segmentation is a property of the data from the moment it is normalized, not a read-time afterthought.
4. **Conform + load.** US Core / profile validation with `$validate` gating; reconciliation gates (counts in = loaded + rejected, per batch, alarmed); upsert into the FHIR store with Provenance resources per load. The record is the single source of truth.
5. **Project + propagate — how domains reach the graph and everything else.** Every committed record change emits a domain event (C2 envelope, memberId-partitioned) via change-data-capture (ADR-006: transaction outbox vs FHIR Subscription; dual-write is banned). Downstream projectors consume independently: the **graph projector** (per-domain mapping spec: which resources become which node/edge types — the demo's 52-node/67-edge schema is the target seed; Part 2 data projects only as restricted nodes honoring its labels), the **SDE signal intake**, and **metric projections**. The graph is derived state — rebuildable from record replay, never a source of truth. This is the role-separation doctrine made mechanical.

**Lane-agnostic transforms.** Each domain declares its arrival modes — batch (monthly 834, daily/weekly claims, nightly rosters, CBO flat files, HMIS extracts), micro-batch (QE CCD queries), stream (ADT, screening submissions, referral-status webhooks, PGD). Stages 2–5 are pure functions per doctrine 7, packaged twice from one implementation: as DAG step containers (batch lane) and as stream consumers (stream lane). One transform codebase, both lanes — divergence between batch and stream logic is a defect class, banned by construction.

**Named social + behavioral ingestion paths (no longer implicit):**
- *Social:* in-product AHC HRSN screening (stream → SDOH T1 with provenance); closed-loop referral platforms (Unite Us-class — the NY SCN lead operates one; webhook/API + flat-file export); CBO flat files over SFTP (the lowest-common-denominator path, treated as first-class); housing/HMIS extracts; Z-code capture from claims (T3 shadow).
- *Behavioral:* BH claims (T3); BH clinical via QE feeds where consent allows (T2/partial T1); **SUD data exclusively through a Part 2-segmented lane** — labeled at stage 3, stored with segmentation, projected restricted, and never surfaced to signals or agents without a consent check at read time.
- *Member-reported:* app/SMS questionnaire responses (stream, T1, provenance-tagged as patient-generated).

**Who decides what (the answer to "are agents assumed to handle this"):**
- *Doctrine — binding now (this section, §4, C-register):* the five stages, staging tier existence, lane-agnostic transforms, segmentation-at-transformation, propagation-by-projection, formats supported, source-of-truth rules.
- *Specialist design — within doctrine (Phase 2):* per-source adapter specs, DAG definitions, per-domain graph mapping specs, quarantine/remediation workflow detail, per-feed reconciliation thresholds.
- *ADR — spine decides against the load model (Phase 1):* store choices (ADR-001, -002, -005), orchestration posture (ADR-003), CDC mechanism (ADR-006).

## 6A. Specialist direction packs (new in v10 — binding inputs; each pack is what good looks like, not the design itself)

**DP-1 Graph & Context (G1).** The ontology seed is fixed, not invented: node taxonomy from the demo schema (Person, CareTeam member, Condition, CareGap, SDOH barrier, Encounter/Event, Intervention/Referral, Coverage/PA, Agent action) with the 52-node/67-edge demo graph as the reference instance. Three semantic rules bind: (1) **temporality** — events carry time; the graph answers "what happened around what," so edges are dated and the journey is reconstructable; (2) **causality is asserted, never silently inferred** — a causal edge (barrier blocks care) carries provenance for who/what asserted it (screening answer, clinician note, agent hypothesis flagged as hypothesis); associative edges are the default; (3) **the five demo lens filters are the acceptance queries** — the projected store must answer them (whatever ADR-001 picks) with the D3 screen consuming real results. The graph informs reasoning; it never acts (role-separation doctrine restated as an acceptance test).

**DP-2 Signal Disposition (G2).** A signal is a typed event about a member from any projector: care gap opened/closed, ADT admit/discharge, screening result, missed appointment, referral stall, denial, PA status change. The disposition decision model is the demo's coordinated-touchpoint semantics made real: for each signal batch per member, decide **act now / suppress (with reason) / delay (to a coordination window) / bundle into a single touchpoint** — the "5 approved, 3 suppressed, 1 delayed, one coordinated touchpoint" screen is the acceptance shape. Disposition policy is **data, not code** (contact-frequency caps, channel preference, consent scope, priority scoring, workforce capacity), per the conventions' adapter pattern, so a state can tune it without a deploy. Every disposition is explainable (which policy fired) and audited. Ordering per member is guaranteed by the memberId partition (C6); fatigue rules are cross-signal, which is why the SDE consumes the stream lane, not point calls.

**DP-3 Agent runtime (G4).** First agents are named, not open: (1) outreach/engagement agent (executes SDE-approved touchpoints), (2) referral coordination agent (closes the referral loop, escalates stalls), (3) PA/documentation agent (drives stage-3/O-8 on the goldenThread machine). All three launch HITL: they propose, the existing work-queue inbox is the human gate — **reuse the goldenThread work-queue and evidence-viewer patterns; do not build a second inbox.** Unactioned HITL items carry escalation defaults (SLA per priority tier, then escalate up the care-team hierarchy, then park with an audit trail — never silently expire). Manifests per conventions v2 §10 (tool allowlist, autonomy tier, escalation, PHI posture). The autonomy dial is per-agent-per-deployment configuration; promotion beyond HITL is an operational decision recorded in the manifest, never a code change.

**DP-4 Care plan (G5).** The acceptance oracle, so "rigor" is testable: (1) golden fixtures — a reviewed set of member contexts with expected plan characteristics, signed off by the Medical Expert lens, run as regression; (2) property invariants — no goal without an intervention, no intervention contradicting an active contraindication, every clinical recommendation carries a guideline citation (ADA/USPSTF/HEDIS-class source id), SDOH barriers present in context must be addressed or explicitly deferred; (3) FHIR conformance — output maps to CarePlan/Goal/Task/ServiceRequest profiles per C4; (4) O-7 criteria content lands flagged not-SME-reviewed until GB-3 sign-off. The generator stays deterministic; any LLM narration sits on top per the guardrails.

**DP-5 Load model + non-functional budgets (X1, consumed by all).** Planning parameters for the spine (adjust with evidence, not silently): pilot = county scale ~50K members; state = NY Medicaid scale ~7M. Feed assumptions: 834 monthly full + weekly deltas; claims weekly; ADT continuous; screening continuous. Default p95 budgets, binding until the spine re-derives them: person-context read ≤ 300ms; graph lens query ≤ 2s; signal → disposition decision ≤ 5s; ADT receipt → signal ≤ 60s; 834 batch landed → loaded ≤ 4h; dashboard view-model read ≤ 1s. Retention: landing zone raw kept per audit policy (default 7 years, configurable); quarantine TTL 30 days with alarmed expiry. Tenancy: single-tenant per state deployment in v1 — isolation by deployment (X3 configurator), never by code branching.

**DP-7 Identity resolution semantics (new in v11 — consumed by pipelines, record, graph, everything).** The match engine is real; production identity needs three semantics the code does not yet carry: (1) **survivorship** — when two sources disagree on a field, a source-ranked rule set (config data, not code) decides the golden value, with per-field provenance retained; (2) **merge/unmerge** — when a possible-match (60–90 band) later resolves to a confirmed match, a merge event flows through C10 and every projector rekeys by replay (no in-place key rewrites); unmerge is the same event class in reverse, and both are audited — merge handling is why projector-rebuild-from-replay is non-negotiable; (3) **provider + organization identity** — NPI-anchored, same survivorship discipline, feeding G7's shared provider model (O-6). Directional default: the record stores source-attributed facts; the golden view is a projection — so survivorship rules can change without data loss.

**DP-6 Adequacy (G7).** Thresholds (time/distance, ratios, wait-time) are configurable data reviewed annually — never constants; dashboards consume shared view-models (the G6 lesson); the compliance report (O-5) is generated from the same view-models so screen and audit evidence can never disagree.

## 11. Operating rules for all subsequent iterations (v12 — from the run retrospective, binding)

- **R1 Artifact-existence gate.** An agent's "completed" report is accepted only when its named output files exist on disk with plausible content. The orchestrator verifies file presence before advancing a phase; a run where reports and artifacts disagree halts immediately. (Origin: six agents reported success while a harness fault meant zero files were written.)
- **R2 Harness probe before fan-out.** Every multi-agent phase starts with one cheap probe agent exercising Read, Bash, Write. Fan-out launches only on a clean probe. Cost: seconds; the failure it prevents cost ~290K tokens.
- **R3 Orchestration fallback ladder.** Scripted orchestration → direct parallel agent calls → inline execution, in that order, switching on first infrastructure failure rather than retrying the broken layer.
- **R4 Durable inputs.** Any owner-supplied artifact (spreadsheet, document, directive) is copied into the repo-synced coalition folder the moment it arrives. Conversation context is not storage; session compaction destroyed the use-case workbook once and never gets a second chance.
- **R5 Phase-boundary checkpoints.** Each phase's outputs are delivered and synced to the owner's disk before the next phase starts. A checkpoint is the recovery point; RECOVERY.md carries run id, resume command, phase state.
- **R6 Bridge independence.** The device bridge is never on an iteration's critical path: syncs queue and retry; git commits execute on the owner's machine (the bridge cannot unlink files, which git requires); docs-only commits use --no-verify; code commits let the hooks run.
- **R7 Prose files over schemas.** Agents write markdown deliverables to named files and return short summaries. Structured-output schemas are reserved for tiny verdict tuples; rich content forced through JSON schemas failed five consecutive times where a verdict file plus a mechanical rule (packViolations >= 1 or rubricFailures >= 2 → re-run) worked first try.
- **R8 Input inventory gate.** Before launch, every file a context manifest references is verified present in the staged copy; the staging inventory ships with the manifests. Two specialists lost source access this run because the staged tree omitted `src/app` and `docs/`.
- **R9 Directive intake.** Mid-run owner directives land immediately as numbered addendum files in the inputs folder; agents launched afterward read them; the finalizer reconciles directives that arrived after an agent already ran, and says so.
- **R11 Tarball sync for code waves (v12.1).** A wave changing more than ~10 files ships as one archive: single delivery, single commit, extracted on the owner's machine. Per-file transfer is for small sets only.
- **R12 Opportunistic commit queue (v12.1).** Disk sync never sits inline on the work path. Deliverables append to a queue; the queue flushes at the next turn start when the bridge reports connected. A failed flush waits; work continues.
- **R13 No hand-transcription of machine data (v12.1).** Ids, uuids, hashes, and paths move between tools programmatically or in immediately-verified small batches. A placeholder-format check runs before any batch that had manual handling.
- **R14 Visible heartbeat (v12.1).** Long working stretches emit milestone updates as they happen; the owner should never have to ask whether the run is alive.
- **R15 One canonical ratchet baseline (v12.1).** `quality-baseline.json` has exactly one source of truth in the repo; regeneration happens only in a refactor-only change with the count direction stated. Parallel regenerations are reconciled immediately in favor of the stricter set. Orchestrator owns the authoritative gate run; agents verify only their own scope.

### Build-phase lessons (v13 — from Iterations 0-2, binding on Iterations 3+)
- **L1 Fakes are necessary, not sufficient.** Every component with a fake (pg-mem, in-memory graph/Temporal) carries a short fake-fidelity ledger naming what the fake does NOT model; the Docker-guarded testcontainer spec is a REQUIRED CI gate for those properties. No stateful component is "done" on fake-green alone. (Origin: outbox passed pg-mem but had real multi-writer Postgres bugs.)
- **L2 Convergence is first-class.** A convergence/adversarial wave is budgeted every iteration and aimed at cross-agent assumptions; it found every material defect across Iterations 0-2, the build waves found none.
- **L3 Pre-allocate the namespace before fan-out.** The iteration context reserves seam ids, module paths, and event-type names; agents claim from the list, never invent. (Origin: SDE seam-id collision with sdResourceData.)
- **L4 Concurrency correctness in the DoD.** Any stateful/concurrent component's DoD includes real-Postgres multi-writer assertions (unique constraint, atomic sequence, compare-and-set claim) as authored testcontainer specs, not discovered in convergence.
- **L5 Two progress numbers.** Report tests-passing AND components-with-live-integration-executed. The second is 0 in the build sandbox (no Docker); that is the honest maturity ceiling until the owner's CI runs the specs.
- **L6 Keep the wave unit.** probe -> 2-3 parallel build agents on disjoint trees -> convergence -> orchestrator authoritative gate -> one tarball sync. Scale by adding waves, not widening an agent.
- **L7 Templatize the repeatable unit.** Before the domain-coverage iterations, author one golden adapter+mapping template; each of the remaining 16 record domains is then a fill-in.
- **L8 One sync per iteration boundary.** Never inline a disk sync between waves; the bridge is unreliable and R12's queue only helps when syncs are off the critical path.
