## 3. Target Architecture

Everything in this section is TARGET state. The design instantiates §4A exactly: five stages, staging tier, lane-agnostic transforms, segmentation at transformation time, propagation by projection only. No deviations; none needed.

### 3.1 Stage skeleton (shared by every feed)

| Stage | Component | Store | Output |
|---|---|---|---|
| 1 Land | Per-source connector writes raw payload immutably to object storage; catalog row written (landingId, source, feed, receivedAt, objectKey, sha256 checksum, batchId, contentType) | S3-compatible object store + Postgres catalog table | `pipeline.landed` evidence entry; correlation id minted here |
| 2 Stage + validate | Format-structural validator (X12 envelope, CCD schematron, HL7v2 MSH/segment grammar, CSV header contract, JSON schema) | Staging store (Postgres, parsed-but-unnormalized entries) + quarantine store | Accepted entries to stage 3; rejects to quarantine with PHI-safe report |
| 3 Transform + enrich | Source adapter normalizes to the canonical domain model; terminology normalization; identity resolution (DP-7); consent + Part 2 labeling; provider NPI resolution | none (pure function; lane harness supplies I/O) | Normalized domain records with consentContext + provenance |
| 4 Conform + load | US Core `$validate` gate; loader commits FHIR upsert + Provenance + outbox row in ONE transaction; reconciliation gate closes the batch | HAPI (FHIR store) + outbox table | Loaded resources; `record.loaded` evidence; reconciliation report |
| 5 Project + propagate | Outbox relay publishes C2 events in per-member commit order to the Kafka-API backbone | backbone topics per load model §3 | C10 events; projectors consume independently |

Stages 2..4 are pure functions with injected clock/IO (conventions §7), packaged twice from one implementation: a batch step-container harness and a stream consumer harness. Divergence between lanes is banned by construction; the contract test runs the same transform fixtures through both harnesses and diffs the outputs.

### 3.2 Per-source adapter specs

Each adapter is a registered module under `src/lib/pipeline/adapters/<source>/` following the NormalizedPolicy pattern (extractor emits raw, adapter normalizes, engines see only the canonical model; extending a source registers an adapter, never edits shared code). Every adapter declares: formats, lane(s), cadence, target C9 domains @ tier, identity fields used for matching, segmentation exposure, reconciliation unit. Common to all: idempotency key = `<feed>:<batchId or messageId>:<recordKey>`; quarantine at entry granularity, never batch granularity, except structural envelope failure which quarantines the file.

#### A. X12 834 enrollment (batch; P1)

- Formats: 834 5010; monthly full file + weekly deltas over SFTP.
- Yields (C9.2): coverage T1, demographics T1.
- Stage 2: ISA/GS/ST envelope validation, segment grammar, control-number continuity check (gap in ISA13 sequence alarms; duplicate control number rejects the file as already-processed, idempotent by construction).
- Stage 3: normalize INS/NM1/DMG/HD loops to canonical `EnrollmentSpan` + `MemberDemographics`. Identity: full demographic trait set to the match service; an 834 is identity-authoritative for its own subscriber id, so a no-match creates a new anchored identity rather than a work item (source of member existence). Survivorship: 834 ranks first for coverage fields, configurable per `data/survivorship-rules.json`.
- Stage 4: Patient + Coverage upserts (US Core Patient, Coverage), Provenance per load. Full-file runs are diff-loads: the adapter computes adds/changes/terms against current coverage state so a monthly full file emits only real change events, not 7M no-op events. ASSUMPTION: full-file diff semantics acceptable to the owner; the alternative (emit-all) breaks the batch-class event budget by an order of magnitude.
- Events: identity.member.anchored, identity.traits.updated, coverage.enrolled, coverage.changed, coverage.terminated.
- Reconciliation unit: member records per ST transaction; counts in = loaded + rejected, exact, alarmed.

#### B. X12 837/835 claims + remittance (batch; P1)

- Formats: 837P/837I 5010, 835; weekly SFTP batch.
- Yields: financial facts T1 (Claim, ExplanationOfBenefit; the golden thread chain, C9 #16); clinical shadows T3 (encounter/condition/procedure/medication inferred from claim lines, C9 #3/#4/#7). Tier labels are stamped in the envelope source.tier field and on the projection; T3 never presented as T1 (C9.1 binding rule).
- Stage 3: claim-line normalization; dx codes to Condition shadows (ICD-10), procedure codes to Procedure shadows (CPT/HCPCS), pharmacy claim lines to medication shadows; rendering/billing provider NPI resolution; care-team attribution shadow (C9 #10 T3). Z-codes on claims become SDOH T3 shadows (C9 #13 P1 target).
- Stage 4: Claim/EOB as T1 resources; shadow resources tagged with a shadow provenance profile slice so consumers can filter by tier. 835 links payment to claim (payment.posted event), closing the golden thread's delivery-to-payment hop (use-case step 16, P1).
- Events: claim.received, claim.adjudicated, payment.posted, plus shadow-domain events carrying tier T3.
- Reconciliation unit: claims per functional group; plus a financial control total check (sum of paid amounts in 835 vs loaded EOB totals, exact, alarmed).

#### C. Pharmacy dispense feed (batch daily; P1)

- Format: NCPDP-derived flat extract or payer-standard CSV over SFTP. ASSUMPTION: the pilot source delivers a delimited extract, not raw NCPDP telecom; spike SP-3 confirms.
- Yields: medication dispense T1 (C9 #5, MedicationDispense per C4), NDC normalized to RxNorm.
- Stage 3: NDC-to-RxNorm mapping via terminology service; prescriber NPI resolution; days-supply/fill-date normalization (adherence signals for the SDE MVR).
- Events: medication.dispensed.
- Reconciliation: row counts + distinct-member counts vs file trailer record when present, else counts in = loaded + rejected.

#### D. Provider directory loader (batch nightly; P1; O-2)

- Format: payer/state provider extract (CSV or FHIR bulk). Yields: care team/attribution T1 foundations (C9 #10), the G7 shared provider model.
- Stage 3: NPI-anchored provider identity per DP-7 (same survivorship discipline as members: source-ranked golden view over source-attributed facts); specialty taxonomy normalization (NUCC); location geocoding for adequacy time/distance. ASSUMPTION: geocoding uses an offline dataset or a licensed service at the IaC layer; core sees coordinates as data (C7 compliance).
- Stage 4: Practitioner, PractitionerRole, Organization, Location upserts.
- Events: care-team.attributed (where attribution present), provider-directory updates ride identity.traits.updated for provider identities.
- Also behind this seam family: gold-card roster feed, denial-rate feed (O-2). Each is a small CSV/JSON feed landing through the same five stages (trivial transforms), loaded into the stores that currently back the mock `goldCardSource` / `denialRates` seams, with the C3 contract test run against mock AND real.

#### E. CCD/QE micro-batch (micro-batch; P2)

- Format: C-CDA 2.1 CCD XML, pulled query-driven from a QE (Hixny-class) on care-event notification, or pushed. Cadence tracks ADT (~200/min state daytime peak).
- Yields: mostly T2 (CCD as DocumentReference, C9 #20) with partial T1 where coded: problems (C9 #4), meds prescribed (#5), lab results LOINC-coded (#6), allergies (#9 partial T1), care team (#10), immunizations T2 (#8).
- Stage 2: XML well-formedness + CCD schematron. Schematron failures quarantine the document; per-section extraction failures at stage 3 quarantine the entry, not the document (golden-path hop 3 rule).
- Stage 3: section extractors (Results, Problems, Medications, Allergies, Immunizations, Care Team) to canonical models; local codes map through the terminology service; unmappable code quarantines the entry. Identity via CCD header demographics through the match engine; a 60..90 band score parks the document on the unmatched-work queue, never loads under a guessed identity (golden-path hop 3).
- Stage 4: discrete resources where coded (tier T1) + the whole CCD as DocumentReference (tier T2) + Provenance linking both to the landing id.
- This is the golden-path feed: hops 0..5 of golden-path.md are the acceptance walkthrough for this adapter.

#### F. ADT HL7v2 (stream; P2)

- Format: HL7v2 ADT (A01/A03/A02/A04-class) from the QE. Ingress: MLLP listener or QE-provided REST relay; spike SP-4 decides. Ingress process lands the raw message (stage 1) then publishes to the raw-intake topic; stages 2..5 run as stream consumers.
- Yields: encounter events T1 (C9 #3), the SDE's admit/discharge signals.
- Budget: ADT receipt to signal <= 60s (DP-5); per-hop budget <5s per load model §6.
- Stage 3: MSH/PID/PV1 normalization; identity via PID demographics; facility NPI resolution; a possible-match ADT parks on the unmatched queue with an aging alarm (an unmatched admit is operationally urgent; alarm at 15 min, ASSUMPTION).
- Events: encounter.admitted, encounter.discharged, encounter.transferred, encounter.ed-arrival.

#### G. In-product screening (stream; P2)

- Format: FHIR QuestionnaireResponse from the platform's own BFF (AHC HRSN-class instrument). This is internal traffic; it still passes stages 1..5 (landed, validated, normalized) so provenance and replay hold for platform-born data. The BFF route is the connector.
- Yields: SDOH T1 with patient-reported provenance (C9 #13, #18); Gravity SDOHCC profiles per C4; positive screens create sdoh.barrier.identified with Z-code coding.
- Events: assessment.submitted, sdoh.screening.completed, sdoh.barrier.identified.

#### H. Closed-loop referral webhooks (stream; P2)

- Format: JSON webhooks from a referral platform (Unite Us-class; the NY SCN lead operates one), plus periodic flat-file export as the completeness backstop (the two are reconciled: webhook stream vs export file counts, weekly, alarmed on drift >1%, ASSUMPTION threshold).
- Ingress: authenticated BFF route `/api/ingest/referral-webhook` (BFF-only invariant; signature verification; replay-safe by delivery id), lands raw, publishes to raw-intake.
- Yields: referral T1 incl closed-loop status (C9 #12).
- Events: referral.initiated, referral.accepted, referral.stalled, referral.completed. Stall detection is NOT computed here; the pipeline records status facts; stall inference belongs to the SDE side (role separation).

#### I. CBO flat files over SFTP + HMIS extracts (batch; P3; first-class by doctrine)

- Format: CSV/pipe-delimited, partner-variable. This is the lowest-common-denominator path and is engineered as a product surface, not an exception: a per-partner feed manifest (data, not code: `pipelines/feeds/<partner>.yaml`) declares column contract, delimiter, encoding, header row, identity fields, target domain mappings. Onboarding a CBO = authoring a manifest + fixtures, zero code. A generic flat-file adapter executes manifests.
- Stage 2: header/column contract validation against the manifest; row-level type checks. Quarantine tolerances are the loosest of any feed (see §3.5) because supplier data quality is the known reality; the remediation workflow (supplier notice with PHI-safe row references) is the primary path, not an edge case.
- Yields: SDOH service data T1 (C9 #13 P3), HMIS housing T1.
- Identity: flat files carry weak identifiers; expect heavy 60..90 band traffic to the unmatched queue; the queue's human resolution UI is the goldenThread work-queue pattern reused (DP-3 rule honored: no second inbox; unmatched-identity items are a work-queue item type).

#### J. Part 2 SUD lane (P3; segmented from birth)

- Not a distinct transport: SUD-bearing content arrives inside claims, CCD, BH feeds. The lane is a labeling + handling discipline: stage 3 runs every normalized record through the segmentation rule set (data: `data/segmentation-rules.json`, value-set driven: SUD ICD-10 ranges, medication lists such as buprenorphine/methadone RxNorm classes, provider-type triggers per 42 CFR Part 2). Matches stamp `consentContext.part2Restricted: true` + segment labels on the canonical record, the FHIR resource (security labels), and the C2 envelope. Projectors without Part 2 clearance drop by envelope inspection alone, never payload parsing (C10). Read-time consent checks stack on top (C1); transformation-time labeling is the floor, per §4A. Retrofitting is a rebuild, therefore the labeler ships in P1 with the rule set active from the first claims load (BH T3 shadows are already in P1 scope, C9 #14).

### 3.4 Staging, quarantine, remediation

Quarantine record (Postgres, PHI-safe by construction): quarantineId, landingId, entryRef (document id / segment position / row number), feed, ruleId, ruleMessage (codes and counts only, never clinical content or names), quarantinedAt, status (open / remediated / expired), remediationAction, actor. TTL 30 days with alarmed expiry (DP-5).

Remediation workflow (general, all feeds):
1. Rejection report per batch, PHI-safe, generated at stage-2 close and stage-3 close; delivered to the operations audience (D7 runbook subject) and, for supplier-caused rejects, exported as a supplier notice referencing row/segment positions, never content.
2. Remediation actions, each audited to the evidence ledger: (a) rule fix (mapping/terminology/manifest change, shipped as data or code, then `dag-replay` from landing); (b) supplier resend (new file supersedes; duplicate control-number protection makes resends safe); (c) manual entry resolution for identity holds (work-queue item, DP-3 reuse); (d) accept-expire for junk (explicit, attributed, never silent).
3. Replay is always from the landing zone by landingId; staging and downstream state are rebuilt, never patched in place. Idempotency keys guarantee no double-load.

Unmatched-identity queue: possible-match (60..90) entries hold the normalized record in staging keyed by a provisional source-attributed identity; a human resolution (work-queue) either confirms (merge event per DP-7, projectors rekey by replay) or creates a new identity. Aging alarms: ADT 15 min, batch feeds 72h (ASSUMPTION, operations-tunable data).

### 3.5 Reconciliation gates and thresholds

Hard gate on every batch (binding, §4A stage 4): entries in = loaded + rejected, exact, per batch, alarmed on any mismatch. A batch that fails the equality never closes; it pages.

Quarantine-rate thresholds per feed (warn = alarm + continue; halt = stop the DAG, page, batch stays open). All values ASSUMPTION, shipped as data (`pipelines/feeds/thresholds.json`), tuned with the first real feeds per the load model's replace-with-measured rule:

| Feed | Warn | Halt | Extra gates |
|---|---|---|---|
| 834 | >0.5% entries | >2% | Control-number continuity; member-count delta vs prior full file >5% warn |
| 837/835 | >2% | >5% | Financial control totals exact; 835-to-837 claim linkage rate <95% warn |
| Pharmacy | >2% | >8% | NDC-to-RxNorm map rate <98% warn |
| Provider directory | >1% | >5% | NPI checksum validity; active-provider count delta >10% warn |
| CCD/QE | >5% docs | >15% | Coded-section extraction yield tracked per QE (T1 yield metric feeds D1 sheet 3) |
| ADT | >1% msgs | n/a (stream: DLQ + alarm, no halt) | Sequence-gap detection per facility |
| Screening | >0.5% | n/a stream | Internal source; failures are platform bugs |
| Referral webhook | >1% | n/a stream | Weekly webhook-vs-export reconciliation, drift >1% alarm |
| CBO flat file | >10% | >25% | Per-partner manifest conformance rate reported to supplier |

Every gate result is an evidence-ledger entry (`pipeline.reconciled`) with counts, correlation id, threshold verdicts: the compliance audience's per-load audit trail (O-5 consumer).

### 3.6 Identity resolution integration (DP-7)

- The match service (`src/lib/identity/matchService/`, new, wrapping the existing Tier-A `matchEngine.ts` unchanged) is called at stage 3 by every adapter. Blocking keys (DOB, zip, phonetic last name per load model §4) bound candidate sets to <=50 (alarmed if exceeded); scoring on a worker_threads pool per the load model.
- The record stores source-attributed facts: every identifier and demographic fact carries its source system (Patient.identifier slices per source; source extensions on demographics). The golden demographic view is a projection computed by survivorship rules (`data/survivorship-rules.json`: per-field source ranking + recency tiebreak, config data, not code), so rule changes never lose data (DP-7 directional default).
- Merge/unmerge: when a possible-match resolves to confirmed, the identity service commits the merge fact + outbox row (identity.member.merged, both ids, survivor id) in one transaction; projectors rekey by replay, never in-place (C10.2). Unmerge is the same event class in reverse. Both attributed and audited. The pipeline pair builds the event emission and the pipeline-side behavior (staged records under a merged id re-attach on replay); projector rekey behavior belongs to each projector owner and is asserted by the shared rebuild-from-replay contract test this pair publishes.
- Provider identity: same discipline, NPI-anchored, survivorship over directory + claims + CCD sources; feeds the O-6 shared provider model.

### 3.7 Segmentation at transformation time

Per §3.2.J: the labeler is a stage-3 pure function over the canonical record + segmentation rule set (data). Labels land in three places atomically: canonical record, FHIR resource meta.security (C4), C2 envelope consentContext. Rule set governance: rule changes are versioned data PRs; a rule change triggers a targeted re-label replay of affected domains (dag-replay scoped by domain + date range). Read-time enforcement is C1's job on top of these labels; this pair's obligation ends at labels-correct-at-rest, asserted by fixture tests (SUD claim fixture in, part2Restricted out, at every stage boundary).

### 3.9 US Core validation harness with $validate gating

- Runtime gate (stage 4): every load calls `$validate?profile=<C4 profile>` against HAPI as an async boundary step before the transactional commit (load model §5: validation never inside the synchronous write path; the loader validates then commits). Spike SP-2 measures; if HAPI `$validate` cannot hold the window, the fallback inside the same seam is an in-process validator (HAPI validator library as a sidecar container) with HAPI `$validate` retained as the conformance oracle in CI. ## 8. Scale Posture

- Throughput vs load model: 834 full file 7M records in the 4h budget = 486 rec/s across 16 loader workers at 35 rec/s each (worker floor is the commitment; per-worker rate ASSUMPTION per load model §4). Claims 234 rec/s in a 4h window. Pharmacy ~16 rec/s. ADT 200/min daytime peak in the stream lane with per-hop budgets <5s, 60s end-to-end. Batch-class event emission ~470 events/s (~28K/min) during load windows, exempt from stream budgets by envelope class declaration, post-window catch-up alarm 1h (C6 traffic classes).
- Partition key: memberId on every topic (C6); per-member ordering is what merge replay and the SDE require. Partition counts per load model §3 (domain-events 12 pilot / 96 state), set at topic creation, never rekeyed mid-flight.
- Idempotency: every step and consumer keyed (`<feed>:<batchId>:<recordKey>` steps; eventId dedupe consumers); duplicate 834 control numbers reject as already-processed; replays safe end to end.
- Backpressure: batch lane self-throttles by worker count; stream lane consumers lag rather than drop (at-least-once), lag is a first-class SLO metric per consumer group; DLQ per topic with mirrored keying; halt thresholds (§3.5) stop batch DAGs rather than flooding quarantine.
- Match scoring: blocking keys bound candidates <=50 (alarmed), worker_threads pool of 4 per pod, 2 pods state / 1 pilot (load model §4).
- Budget compliance: all six DP-5 budgets adopted as stated; none dropped, none re-derived (spine-only right). The stage-4 $validate cost is the one identified threat to the 4h window; mitigations in §3.9, measured by SP-2, escalated to the spine if batching + caching cannot hold it (a budget escalation, not a silent drop).
- HAPI posture consumed as specified (load model §5): validation as async boundary step, bulk loads via batched transaction bundles sized to windows, CQRS reads elsewhere.

## 15. Risks

Ranked. Each names its mitigation contract/doctrine or its escalation.

1. External feed access timing (QE contracts, payer extracts, referral platform keys) gates P1/P2 dates. Mitigation: every adapter is fixture-complete and contract-tested before connectivity exists (Tier-A honest, BackboneNotConfiguredError until configured); GB-class blockers named per feed in D1 rather than silently slipping. Escalation: owner sequencing decision if a P1 feed has no source by build start.
2. Stage-4 $validate throughput threatens the 4h 834 window. Mitigation: SP-2 measured early; batching + caching inside the gate seam; spine escalation for budget re-derivation if both fail (never a silent drop).
3. Terminology licensing/content (SNOMED, RxNorm, schematron packs) is a procurement dependency with deployment-portability implications. Mitigation: SP-6; content shipped as data per deployment via IaC; C7 keeps core clean. Escalation: compliance/legal for license posture per state.
4. Identity false merges corrupt the record silently. Mitigation: DP-7 semantics built exactly (60..90 never auto-links, merges are events, projectors rekey by replay, unmerge is first-class); `rebuildFromReplay.contract` + SP-7 prove it before scale; alarmed blocking-key overflow.
5. Flat-file partner data quality floods quarantine at P3. Mitigation: manifest gates at stage 2, loosest-but-real thresholds (§3.5), supplier-report remediation loop as a designed workflow, quarantine TTL alarmed.
6. Batch-window projector lag surfaces as stale screens during loads. Mitigation: C6 traffic-class exemption is explicit and alarmed (1h catch-up); dashboards read view-models with declared freshness; documented in the ops runbook rather than discovered in production.
7. Part 2 rule-set gaps (an SUD-bearing record missed by the value sets) create a compliance exposure. Mitigation: segmentation rules are versioned data with compliance sign-off gates; targeted re-label replay on every rule change; conservative default posture for BH-provider-sourced content (label when in doubt, read-time consent still applies). Escalation: GB-7 security review consumes the labeler's test evidence.
8. Diff-load semantics for 834 full files (ASSUMPTION §3.2.A) may conflict with owner audit expectations (some programs require full-file event emission). Escalation: explicit owner decision; the alternative re-sizes the batch-class event budget with the spine.
