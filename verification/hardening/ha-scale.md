# HA + Performance/Scale hardening review

Persona: High-Availability + Performance/Scale adversary (on-demand scale persona).
Scope: production HA posture (multi-instance, real Postgres, real volume, rolling deploy, backend failure).
Mode: READ-ONLY. Findings only, no source modified.
Baseline: `/home/claude/baseline`, reviewed 2026-08-23.

Reasoning was branched tree-of-thought across seven failure/load modes: (1) statelessness across >1 instance and restart, (2) failover + graceful degradation, (3) connection-pool exhaustion / external-call timeouts, (4) backpressure / unbounded queues / poison loops, (5) zero-downtime deploy + migration hazards, (6) idempotency/outbox correctness under real multi-writer Postgres, (7) DR / backup-restore.

The build is architecturally honest about most of this: the DB-layer compare-and-set in the outbox (`claimForConfirm`) and the composite-PK idempotency marker are genuinely multi-writer-safe, and the register (GAP_AND_STUB_RISK_REGISTER.md, I9/I10/I11) already logs a number of these as certification residuals. What follows re-derives them from the HA/scale attack surface, ranks by blast radius under load/failover, and adds several the register does not isolate (in-process MemberLock ordering across instances, the unscheduled reconciliation sweep, dual-pool wiring, the synchronous governance contract, in-memory SLA timers).

## Ranked findings

| id | concern | what breaks at scale / failover | severity | owning iteration |
|---|---|---|---|---|
| HS-01 | Per-member ordering relies on an in-process `MemberLock` (`src/lib/outbox/memberLock.ts`, a `Map<memberId, Promise>`), with no member-to-instance partition router. The DB CAS (`claimForConfirm`, `UNIQUE(member_id, sequence)`) prevents duplicate/gap sequences, but NOT cross-instance ordering. | With >1 instance, two requests for the same member land on different instances and drain concurrently. A newer intent on instance B can win `claimForConfirm` and take sequence N before an older intent on instance A. Publish order then diverges from creation order: the C2 per-member ordered event history (the S4-inversion guarantee) holds only within one process. Sequence integrity survives; causal ordering does not. | HIGH | cdc-relay (needs pg advisory lock on memberId, or a real member-partitioned consumer) |
| HS-02 | The reconciliation sweep (`OutboxSweeper.sweep`, `src/lib/outbox/sweep.ts`) is built and correct but is never scheduled: no `setInterval`/cron/worker in `src/app` or `src/lib` invokes it. | Orphaned intents (FHIR write landed, process crashed before confirm/publish) are the exact case the sweep exists to recover. With nothing driving it, after any pod crash or deploy those intents sit `pending` forever and their C2 events never publish. Silent under-delivery that grows with instance count and restart frequency. | HIGH | cdc-relay (scheduled sweep worker + leader election / advisory lock so one instance sweeps) |
| HS-03 | No timeout, retry, or circuit-breaker on the external seams. `fhirServer.ts` alone sets a 30s `AbortController` (and even it has zero retry). `cdsClient`, `pasClient`, `memberMatch`, `bulkClient`, `productionTerminologyService`, and `smartSession` token calls issue `fetch()` with no `signal`/timeout. | A slow or hung MPI / NPPES / terminology / FHIR / token backend holds the Node request handler and its pg connection open indefinitely. Under load this saturates the event loop and the connection pool with no fail-fast and no shed path, so one degraded dependency cascades into a full-instance brownout. No breaker means no graceful degradation. | HIGH | external-seams hardening (per-call timeout + bounded retry + breaker) |
| HS-04 | Connection pools are unbounded and multiplied. Three separate `new Pool({connectionString})` sites (`substrate/bootstrap.ts`, `evidence/store/composition.ts`, `deadLetter/composition.ts`), none set `max` / `idleTimeoutMillis` / `connectionTimeoutMillis`. Worse, producers call the seam selector (`getDeadLetterStore()`, `getEvidenceStore()`) which builds the composition-root pool, so the substrate-bootstrap-wired evidence/deadLetter stores are effectively dead wiring and a second pool exists for the same tables. | Per instance there are at least three pools at the pg default of 10 each; across N instances plus dual-wiring this can blow past Postgres `max_connections` and produce connect storms with no `connectionTimeoutMillis` ceiling. Cold/serverless paths can leak pools (no single-bootstrap guard). | HIGH | substrate (pool sizing/singleton; collapse to one wiring path) |
| HS-05 | Legal-hold registry is an in-memory `Map` (`src/lib/lifecycle/legalHold.ts`, `activeHolds`). Purge and right-to-delete gate on `registry.isHeld(...)`. | A restart drops every hold; an empty registry is indistinguishable from an unloaded one. A subsequent purge/right-to-delete sees `isHeld=false` and proceeds, irreversibly deleting data that is under legal hold. The "never bypass a hold" guarantee holds only within one process lifetime; there is no code enforcement, only a runbook gate. | HIGH | data-lifecycle (durable substrate-backed hold store + load-attestation gate on `runPurge`) |
| HS-06 | Readiness (`deploy/preflight.ts`, `/api/health/readiness`) checks CONFIG PRESENCE, not backend liveness. `runPreflight` is a pure read of env + frozen schema and imports no resolver "so inspecting a seam never has a side effect." | A wrong-but-present `DATABASE_URL`, or a Postgres/FHIR/MPI backend that is actually DOWN, still returns 200 ready. The load balancer routes traffic to an instance that fails every request. Readiness cannot express degradation, so there is no automatic drain-on-dependency-loss; failover depends on an external check that does not exist here. | HIGH | deploy (a liveness variant that pings the DB / key backends, gated to stay PHI-safe and cheap) |
| HS-07 | The value-set governance store interface is SYNCHRONOUS (`putVersion(): void`, `appendTransition(): record`, `history(): []`) and is deliberately excluded from `bootstrapSubstrate` ("synchronous store contract, memory-only"). Default is a process-local in-memory `Map` ledger. | A synchronous contract cannot be satisfied by real async Postgres, so the "production pg-backed factory" is architecturally blocked from being a true durable ledger without an interface change. In mock/seeded each instance holds its own maker-checker + version-lifecycle state: approvals diverge across instances and are lost on restart. An append-only governance AUDIT ledger that is neither shared nor durable. | HIGH | I8A-iii (make the governance store async + substrate-wired, like the evidence ledger) |
| HS-08 | Migration runner (`substrate/migrationRunner.ts`) does read-existing-then-`INSERT` with no `pg_advisory_lock` / deploy serialization. | A rolling (multi-instance) deploy has two pods run `runMigrations` against one DB concurrently; both see an empty ledger row and both `INSERT`, the loser hits `schema_migrations_uk` and throws `PreflightNotReadyError`/startup failure. Not corruption (DDL is `IF NOT EXISTS`), but the losing pod crash-loops mid-rollout, breaking zero-downtime deploy. | MED | substrate (session advisory lock around migrate) |
| HS-09 | No expand/contract discipline or reversible migrations. DDL today is additive (`CREATE ... IF NOT EXISTS`), which is safe, but there is no separation of schema change from code rollout and no down-migrations for the MUTABLE stores (outbox/idempotency/graph/xref). | The first lock-taking `ALTER`/index on a large `outbox_intent` or `dead_letter` table takes an `ACCESS EXCLUSIVE`/index lock while the running code still reads it, stalling live traffic during deploy. There is no rollback path if new code plus new schema must be reverted; the checksum-immutability rule (`ChecksumMismatchError`) forbids editing in place, so a bad migration blocks boot. | MED | substrate (migration policy: online DDL, expand/contract, down-paths for mutable stores) |
| HS-10 | Append-only stores grow unbounded with no TTL/retention/purge: `outbox_intent` is never deleted ("rows are never deleted"), `idempotency_marker` is one row per (consumer,eventId) forever, `dead_letter` keeps every version, evidence ledger append-only. | Under real event volume these tables bloat without bound. The scan-shaped queries below degrade with them, autovacuum pressure rises, and index/heap size eventually dominates latency. No pruning window exists anywhere. | MED | data-lifecycle / I6 (retention windows, partitioning) |
| HS-11 | `dead_letter` `list()` (`pgDeadLetterStore.ts`) does `SELECT ... ORDER BY seq ASC` over ALL versions of ALL records and reduces to latest-per-record in JS, with no pagination and no index-driven latest snapshot. `outbox.all()` and per-member `pendingForMember`/`confirmedForMember` are also full scans of a growing table. | The ops dead-letter surface loads the entire append-only history into memory on every list; as DLQ history and outbox volume grow this goes O(total-rows) and collapses (memory + latency) exactly when an operator most needs it (a large failed feed). | MED | I9 (indexed/paginated latest-snapshot query; `DISTINCT ON` or a current-state projection) |
| HS-12 | Poison-record loop is unbounded and the retry lane is unwired in production. Pipeline dead-letter records carry no retry-count of their own (`reviewAction` retry has no max-retry ceiling / auto-park); the retry-lane registry (`review/lanes.ts`) is an in-process `Map` with NO production lane registered, and it is not covered by the seam-disposition governance gate. | A record that always fails validation can be retried forever with no auto-park (backpressure sink that never drains), while in production the lane is silently non-functional (`retry-lane-not-configured`) so retry does nothing. Per-instance registration also means a lane registered on one pod is absent on another. | MED | I6 (retry budget + auto-park; register + govern production lanes) |
| HS-13 | `failIntent` (`outbox/sequencing.ts`) does an awaited dead-letter append + `drain()` inline in the drain loop and rethrows on write failure (correctly fail-closed for NS-01). The dead-letter store is thereby a hard synchronous dependency of every outbox drain and of pipeline ingestion. | A slow or down dead-letter store stalls or aborts the live outbox drain and, for the pipeline, aborts the whole batch. Correct for durability, but it couples async-spine throughput to dead-letter-store health with no bulkhead: a dead-letter incident becomes an outbox/ingestion incident. Deploy-ordering hazard too (pipeline=production without deadLetterStore=production bricks ingestion). | MED | I6/I9 (bulkhead the failure sink; runbook the deploy-ordering constraint) |
| HS-14 | The workflow/SLA engine (`agentRuntime/engine.ts`, `InMemoryWorkflowEngine`) holds `instances`, `pending`, `timers`, and `memberChains` in in-memory `Map`s and schedules SLA escalation via injected-clock timers (`scheduleTimer`). Labeled a fake, but it is the escalation mechanism. | If driven in a production request path, a restart loses every pending workflow and every scheduled SLA-escalation timer, and timers never fire across instances (the pod that scheduled must be the pod alive at due time). SLA escalations silently drop on deploy/crash; no durable timer/queue backs them. | MED | agent-runtime (durable timer/queue store; leader-driven firing) |
| HS-15 | Zero observability (NS-02): no metrics, tracing, or exported counters for DLQ depth, oldest-open age, sweep lag, pool saturation, external-call latency, or outbox backlog. Correlation id is minted but not aggregated. | Every backpressure and saturation mode above is invisible in production and nothing pages when queues pile up or pools saturate. The system runs blind at exactly the load where HS-02/03/04/10/12 manifest, so failures are discovered by users, not alarms. | MED | observability iteration / NS-02 |
| HS-16 | No DR posture: backup/restore is by-hand `pg_dump` in the runbook only, with no scheduled backup, no PITR, no defined RPO/RTO, and no restore drill. NS-05 live-integration-executed count is 0, so append-only ledger restore (evidence/outbox/graph) has never been exercised. | On data loss or region failure there is no proven recovery path and no bounded RPO/RTO for PHI-bearing append-only ledgers. Durability guarantees are proven only against pg-mem/fakes; a real restore of the ordered outbox/evidence history is unvalidated and could reorder or lose events. | HIGH | certification/pilot (backup automation + PITR + restore drill, RPO/RTO targets) |

## Notes on what is already safe (not findings)

- Outbox exactly-once at the DB layer is real: `claimForConfirm` is a single-statement compare-and-set with a bounded retry on the `UNIQUE(member_id, sequence)` collision, and `enqueue` dedupes on `idempotency_key`. Multi-writer Postgres cannot double-publish or double-sequence. HS-01 is about ORDER, not duplication.
- Idempotency dedupe is a composite-PK insert-and-catch, correct across real pg and pg-mem; the only gap is unbounded marker growth (HS-10).
- Preflight and readiness fail CLOSED (503 on any exception, never default-ready); substrate refuses to boot on blank/absent `DATABASE_URL`. HS-06 is that "configured" is not "reachable/healthy", a narrower gap.
- Migrations are non-destructive and checksum-guarded; HS-08/HS-09 are about concurrency and online-DDL policy, not the current additive DDL.
