# Re-processing & Data-Correction Hardening Findings

Role: re-processing / data-correction adversary (R2 negative-space, red-team). Read-only review of
`/home/claude/baseline`. Lens (tree-of-thought, one branch per scenario): once data is in the platform,
can operations RE-PROCESS and CORRECT it safely? Six branches: (1) dead-letter re-drive, (2) late-arriving
and out-of-order data, (3) corrections / amendments / voids from source, (4) backfill / historical reload
without double-counting, (5) projection rebuild from the event log, (6) reprocessing after a code / mapping
fix. Findings are gaps that block or corrupt a real payer / HIE data-correction operation, whether or not
the GAP register already names them (a deferred gap is still a gap for deployment); the register and CRUD
hardening file are cross-referenced where they overlap.

Verified against source, not plan: outbox `enqueue` dedups on a natural-key `idempotencyKey` and returns
the EXISTING row (`memoryOutboxStore.ts:17-18`, pg `ON CONFLICT`); adapters set that key from the source
natural id with no content hash (`claim:${id}`, `allergy:${allergyId}`, ...); the graph store upserts
nodes/edges `ON CONFLICT DO UPDATE SET props=<incoming>` (`adapters/postgres/store.ts:82-119`); `project()`
has no try/catch (`projector.ts`); no raw-payload / landing store exists (dead-letter `payloadRef` is a
symbolic `batch:...#...` handle, `persist.ts`); the retry-lane registry has no production registration
(`review/lanes.ts`, only re-exported); `replayEvents` / `replayToStore` have no app caller reconstructing
`C2Event[]` from `outbox.all()`.

| RP-01 | corrections + backfill (3, 4) | **Natural-key idempotency silently drops content CORRECTIONS.** `conformAndLoad` sets `idempotencyKey` from the source natural id only (`claim:${id}`, `allergy:${allergyId}`, `assessment:${qrId}`, ...), no content hash / version. `enqueue` dedups on that key and returns the pre-existing row `deduped:true` (`memoryOutboxStore.ts:17`, pg `ON CONFLICT DO NOTHING`), so a re-sent record carrying the SAME natural key with CHANGED content (a corrected amount, a fixed code, a status change) never reaches the FHIR apply or the projector. The dedupe that makes backfill safe makes in-place corrections invisible. | Every source correction that reuses the resource id is swallowed with no error and no dead-letter; the graph keeps the stale value. ## Cross-cutting observations

- **The platform is append-and-overwrite, never correct.** Two mechanisms fight each other: a stable
  natural-key dedup (RP-01) that DROPS any resend, and a last-arrival-wins upsert (RP-03) that OVERWRITES on
  the resends it does admit. Neither is a correction primitive. There is no content version, no
  effective-time compare, and no supersedes / amendment chain, so a source correction is either silently
  swallowed (same key) or silently clobbers newer state (different key, older data).
- **Re-processing mechanisms exist but are not wired.** Retry lanes (RP-08), rebuild-from-replay (RP-05),
  and the raw re-drive of a held record (RP-02) are all built-and-tested-against-fakes but have no
  production binding or backing store. The honest ceiling: the platform can INGEST safely but cannot
  RE-PROCESS in deployment today.
- **Replay only covers the projector half.** Rebuild-from-replay re-derives graph projections from retained
  C2 events, which correctly back-applies a mapping-spec fix, but the transform / terminology half of the
  pipeline is not replayable and raw sources are not retained (RP-04), so the majority of code-fix
  reprocessing cannot reach already-ingested history.
- **What is genuinely safe:** idempotent FHIR PUT + outbox natural-key dedup make a backfill of UNCHANGED
  records non-double-counting, and per-member FIFO sequencing plus merge/unmerge-by-replay
  (`replay.ts`) give correct identity rekeying on rebuild. The gaps above are all in the CORRECTION and
  OPERATOR-SURFACE dimensions, not the replay-arithmetic dimension.
